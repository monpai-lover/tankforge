# 给 VPS 上 Codex 的 TankForge R8.6 完整升级交接

请先读完整文件，再根据服务器的实际部署方式升级。此包包含新版完整 HTML、Linux amd64 静态服务端、完整游戏 `data/`、默认 `config/`、来源／许可、文件指纹和本轮修改源码。打包端没有登录、停止或部署 VPS 服务，亦不以静态检查代替 Linux 实机运行。

## 本轮需要带上的变化

- 移除飞行底部遮挡操作栏的护送任务长条；任务状态继续由原有战局和小地图提供。
- 操控飞机时能看到舰队头顶位置标记，覆盖座舱和第三人称。标记只读取已获准的服务端舰船快照，不让客户端决定伤害或胜负。
- 海水改用用户提供的 Frank Hugenroth 高度波参考进行适配，保留游戏现有海面几何、碰撞与镜头。海水适配为 **CC BY-NC-SA 3.0**，不是 MIT；原作者、参考原文、许可说明及已有 MIT 通知都必须保留。
- 既有 MiG-17 挂载、即时换目标回放、防护查询和联机退出恢复等修复随完整页面保留。

最终 HTML、服务端、源码指纹以包内 `manifest.json` 及压缩包旁的 `.receipt.json` 为准。`source-patches/` 是本轮可审查修改，不是独立可重建的完整源码。完整开发仓库为 <https://github.com/monpai-lover/tankforge>，分支 `codex/r81-airwar-agm-fixes`；打包时的提交、脏状态和实际 canonical app SHA 均记录在 manifest。不要拿仓库中旧 `client/web` npm 入口重新覆盖这个完整页面。

## 先确认线上实际使用的文件

1. 只读检查当前进程、监听端口和服务管理方式，确认运行的是 systemd、容器或其他管理器。systemd 可先查看 `systemctl list-units --type=service --all`，然后读取已确认服务的 `ExecStart`、`WorkingDirectory`、环境文件引用和 unit/drop-in。不要凭目录名猜正在运行的版本。
2. 从实际进程参数确认 `tg-server`、`--page`、`--data` 的绝对路径、绑定地址和端口；读取进程可执行文件路径并记录旧二进制及旧 HTML 的 SHA-256。
3. 查明 Nginx/Caddy 实际站点和 upstream：网页 `/` 与 WebSocket `/ws` 必须指向同一新版服务。确认是否另有静态 `index.html`、旧 CDN 缓存或代理缓存正在覆盖后端页面。
4. 记录实际使用的自定义配置、账号／鉴权、持久化状态、服务环境文件和权限。保留域名、证书、TLS、密码和反向代理配置；不要将它们放进公开交接记录。

## 在新目录校验及试运行

将压缩包和旁边的 receipt 上传到独立暂存目录。先算压缩包 `sha256sum` 并与 receipt 的 `sha256` 精确比较，再用 `tar -tzf` 查看成员。只解压到新目录，原部署目录保持完整。

进入解压后含 `manifest.json` 的目录，执行：

```sh
python3 verify-package.py
sha256sum -c SHA256SUMS
file tg-server
```

Python 校验必须输出 `passed: true`，标准校验清单必须全部 OK。`verify-package.py` 也核对 `SHA256SUMS` 本身；标准 `sha256sum -c` 不包含 manifest 和清单自己的递归哈希，压缩包的外部 SHA 保护完整交接内容。服务端应为 Linux ELF64 x86-64；此包已静态检查无动态解释器、依赖库或可执行栈。

`config/` 是完整安装的默认值，**不能盲目覆盖线上自定义配置**。在新发布目录逐项比较和合并：使用新版静态载具／地图／模型资料，保留现有自定义规则及持久化状态的正确路径、权限和 owner。不要把旧账号、存档或在线运行中写入的数据当成可删除的安装文件。

先用只监听 loopback 的空闲临时端口试运行。下面的 18787 必须先确认未被占用：

```sh
TF_BIND=127.0.0.1 TF_PORT=18787 ./start.sh
```

`start.sh` 默认页面是当前目录的 `tankforge-r86.html`，默认资料是 `./data`。若已核对需要使用不同数据路径，可设 `TF_DATA_DIR`；保留线上服务原有的所有其他必要参数。用独立终端检查 GET `/`，不要用 HEAD 代替，因为现有 HTTP 入口可能不支持 HEAD：

```sh
curl --fail --silent --show-error http://127.0.0.1:18787/ | sha256sum
```

输出必须等于 `manifest.json` 的 `htmlSha256`。继续检查正常启动日志、加载地图和 WebSocket `/ws` 握手／房间流程。临时实例退出时只停止这个已确认的临时进程，不影响旧正式服务。

## 正式切换

1. 先备份实际旧页面、可执行文件、相关配置、服务定义／drop-in 和实际反向代理站点文件；记录绝对路径与指纹。保持旧发布目录可直接回退，不做递归清理。
2. 按线上已确认的管理方式停止旧实例；将正式启动路径或现有发布指针切到已校验的新目录，保留原绑定、环境引用、用户身份和持久化路径。不要把旧页面名留在 `--page`，也不要再使用旧的服务端进程提供新页面。
3. 如果修改了 systemd unit/drop-in，执行对应的 daemon reload，然后启动已确认的服务。若没有修改反向代理，不需改证书或站点；若调整 upstream，先运行配置检查，通过后再 reload 已确认代理服务。
4. 从 VPS loopback 和公开域名分别 GET `/`，核对实际返回 HTML 的 SHA。确认 `/ws` 同源连接到同一新版实例，并检查进程路径、启动参数、监听端口和日志。若代理动态压缩，比较解码后的 HTML 字节；浏览器刷新旧缓存。
