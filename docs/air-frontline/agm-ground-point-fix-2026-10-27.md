# 对地制导武器地面点发射修复

## 已重现的断点

原界面的 `seekerCaptureRequest` 可以生成 `sk.point`，`podTrackRequest` 可以生成 `pod.point`。原生适配器随后用服务端快照刷新显示，但 `air_seeker_control` 只发送单位引用。地面点没有单位引用，因此捕获会在这条边界丢失；旧的 `ctl.selected` 还可能替代玩家刚捕获的地面点。

另一个显示断点是旧 `launchCheck` 的“联机暂不支持对地武器”分支。原生服务器已经负责挂载投放，这个旧提示仍会影响 AGM、制导炸弹、普通炸弹和火箭的状态显示。原生就绪显示必须读取接受后的服务器状态，不能要求只有旧本地导引器才会填写的估计值。

## 接入合同

- 沿用现有空格捕获、瞄准界面及发射键，不引入第二套操作模式。
- 客户端只提交可选的规范化世界瞄准方向 `sight`；地面点请求的 `target` 为空。客户端不提交接触坐标、命中或伤害。
- 服务端从已接受的机体／传感器位置计算有限射线的首个地形或设施接触，并执行武器距离、最小距离、偏角、遮挡、准备和捕获限制。
- 快照通过 `seeker.point` 返回接受后的点；它与真实单位的 `UnitRef` 分开，不用虚构单位表示建筑或地面。
- 新的捕获由成功接受的原生控制命令序号 `accepted_capture_seq` 确认；界面不能借用上一个点的就绪状态。新点请求被拒绝时清除旧的挂载锁定，保留与在途武器有关的独立照射。
- 同一捕获意图跨快照和飞机运动保持稳定，重复心跳不会反复重置捕获。换武器、取消、生命及控制权变更不能继承旧武器的就绪许可。
- TV／IIR 的已发射武器保留接受后的固定瞄点；激光／驾束的在途武器继续依赖有效的照射／支持。吊舱照射与所选挂载的准备状态分别处理。
- 发射、弹药、运动、有限接触、伤害及胜负继续由现有原生权威负责。

客户端的旧地形查询只用于瞄准显示。明确捕获时，只要武器模式、光照和瞄准方向有效，原生服务器仍应有机会检查自身注册的地形／建筑场景；不能因客户端只查到地面、漏了建筑而提前吞掉这次请求。

## 验证记录

新增 `handoff/tests/agm-ground-point-runtime.test.mjs` 从实际应用提取原生控制器、心跳发送、原捕获函数和状态检查一起执行。初次结果为 **0/5**：小牛与吊舱地面点在实际请求中缺少方向，制导炸弹／无制导挂载仍出现旧联机拒绝提示。该测试的渲染射线边界使用有限场景夹具；服务端真实落点、库存与命中另由 Rust 回归验证。

最终客户端专项为 **44/44**，包含实际 runtime 的 8 项回归、22 项地面点控制检查及原有制导武器检查。独立审查发现的捕获确认、控制 epoch、X/P 取消和拒绝后重试均有先失败后通过的回归。确认前的发射请求直接丢弃，不在确认后补发。

原生地面点专项 **11/11**；完整 `tg-server` 执行 **448 项单元测试及 3 项集成测试**，零失败；combat／penetration／missile 的 **239 项测试**通过。完整服务端运行后，以实际导出器更新飞机资料的 `source.appSha256`；逐字段比较证明所有运行时气动、挂载、炮弹、硬件和其他来源段完全相同。最终导出资料上另跑原生地面点专项，完整页面检查与安装检查的结果绑定在交付包的 `validation.json`。
